# Protocol v6 reference

This is the wire format generated by Placebo, intended for runtime and contributor
work. For application development, start with the [typed editor quickstart](../README.md#quickstart).
Use action bindings to generate forms and replies, and action route adapters to
register handlers. Handwritten protocol data bypasses those authoring checks.

Forms carry their configuration as JSON in `data-placebo`: a mutation form's
is `{"version": 6, "action": …, "target": …}`, and a read form's is
`{"version": 6, "read": true}` with `"input_delay_ms"` and `"reveal": true`
when set. Requests use form encoding. A read GETs the page it is on at its
form's query, and a feed's signal or a poll GETs the current page URL, each
with `Accept: text/html` and `X-Placebo-Refresh: 6`. Mutations use POST with
`Accept: text/html`, `X-Placebo-Request: 6`, and `X-Placebo-Page` (the path and
query of the page the form is on). Every mutation
request must come from the same origin: `Sec-Fetch-Site` must be `same-origin`,
or, from a browser without that header, `Origin` must match `Host`. A request
with neither header is allowed (it is not a current browser's cross-site form).
A refused request gets a 403 HTML page a person can read: a cross-site
submission, or a runtime from another protocol version, which asks for a
reload. This assumes same-origin deployment without permissive CORS;
applications still own authentication and record-level authorization.

A mutation form whose payload has an `Upload` field has
`enctype="multipart/form-data"`, and the runtime sends it as `FormData`. File
inputs carry `data-placebo-max-bytes`; the runtime refuses to send files over
it, and the server answers 413 with `X-Placebo-Upload-Limit` before the handler
runs. A file part must belong to a declared file field, and text parts to the
others; an empty, unnamed file part is an absent file. The whole multipart body
is limited to its file fields' limits plus 1 MiB of text and 256 KiB of
framing, and answers 413 beyond that. Only a payload with a file field reads
multipart; any other answers 415, so its body stays under axum's
`DefaultBodyLimit`.

A POST without `X-Placebo-Request` is a native form submission: the browser
sent the form itself, before the runtime loaded or without JavaScript. It runs
the same handler. A successful reply becomes `303 See Other` to its `navigate`
path, else back to the page the form was on (the form's `placebo-page` field,
else the same-origin `Referer` path, else `/`). An `invalid` or `conflict` reply
becomes a full HTML page with the reply's status: `native_forms` sends a GET for
that page through the application with the request's headers, and the rejected
component's mount renders the reply's contents (a `mount_dialog` root also gets
`open`). If that page does not mount the component, or `native_forms` is not in
use, the page shows only the component.

Mutation forms carry reserved fields, which the adapters remove before
decoding. `placebo-base` holds a hash of each visible control's rendered value
(hidden and password controls excluded). For a native submission, a field whose
submitted values hash differently is edited: the handler's reply renders the
submitted values for it instead of its own, the same rule the runtime applies,
and the first control marked invalid gets `autofocus`. `placebo-target` names
the component the form is bound to, so only the submitted form shows those
values; other forms of the same payload type in the reply show what the
handler rendered. `placebo-page` appears only
on forms rendered for a native submission, whose address is the action path.
Payload fields cannot use names starting with `placebo-`.

## Mutation replies

A handler's `reply`, `invalid`, or `conflict` is the component's contents with
HTTP 200 (`applied`), 422 (`invalid`), or 409 (`conflict`). For the runtime,
`native_forms` renders the page named by `X-Placebo-Page` again, as a GET
through the application with the request's headers and cookies (plus any
`Set-Cookie` the handler sent), with the replying component's mount rendering
the reply's contents. The answer is that page (`text/html`) with the reply's
status and headers:

| Header | Meaning |
|---|---|
| `X-Placebo-Outcome` | `applied`, `invalid`, or `conflict`, matching the status |
| `X-Placebo-Action` | the action whose adapter answered |
| `X-Placebo-Rendered` | when the page began rendering, in microseconds; later pages show every write of earlier ones |
| `X-Placebo-Unmounted` | the page does not mount the replying component |
| `X-Placebo-Navigate` | a successful reply's same-site path; the body is empty and the browser goes there |
| `X-Placebo-Page-Missing` | the page answered an error (such as 404); the body is the reply's contents alone |
| `X-Placebo-Page-Error` | the page could not be rendered (no `native_forms`, or no page path); the body is the reply's contents alone |

The runtime morphs the page's `<body>` into the document with the vendored
idiomorph, by these rules:

- A page whose `X-Placebo-Rendered` is not later than the page shown applies
  to the replying component only (`page: "older"`). So does a page rendered for
  a query the address no longer shows, because a read moved it on
  (`page: "moved"`); the page is then read again at the current query. A page with `X-Placebo-Page-Missing` or
  `X-Placebo-Page-Error` applies to it only too, with a `page-missing` warning
  or a `page-error` error.
- A component with a request of its own in flight keeps its node and contents
  (`skippedComponents`, reason `busy`).
- A local unit is a typed control (`data-placebo-field`, keyed by its form's
  action path, none for a read form, and field name) or an explicit `data-placebo-local` subtree,
  which takes precedence over the controls inside it. Units are planned per
  component and outside all components. A unit keeps its node when any control
  in it differs from its default (`defaultValue`, `defaultChecked`,
  `defaultSelected`: the markup the server last rendered) or changed after the
  request was sent. On an `applied` outcome, units with controls in the
  submitting form take the incoming markup unless they changed after sending;
  a read form's units take the page read for them the same way.
  Units without form controls are always kept. A kept unit takes the incoming
  `aria-invalid`, `aria-describedby`, `aria-errormessage`, `disabled`,
  `readonly`, and `required`. A kept or refreshed unit meets its own incoming
  counterpart even if it moved. Any other control that differs from its
  defaults keeps its value.
- `open` on `dialog` and `details`, `data-placebo-stale`, `data-placebo-feed`,
  and `aria-busy` during a request are the browser's and are not changed.
- The document title follows the page's. Focus stays on an element the morph
  keeps; otherwise it moves to the matching element in the new markup, and an
  `invalid` reply focuses the first `aria-invalid="true"` control in the
  component unless the person kept typing.

Every local key, local shape, and nested component root is checked before the
first DOM change; a failure leaves the page as it was. When a mutation's
outcome is unknown (its response was lost, unreadable, or could not be
applied), the component gets `data-placebo-stale` until it shows server state
again. Nothing is retried automatically, and aborting a POST cannot undo a
committed write.

## Reads

A read form is `<form method="get">` without an action, so it reads the page it
is on: `new FormData(form)` becomes the URL's whole query. The runtime puts
that URL in the address with `history.replaceState` as the request is sent, so
replies and refreshes from then on render the page at that query, and fetches
it (`cache: "no-store"`). One read is in flight per page: a new read cancels
the one waiting or in flight (`discarded`, reason `superseded`), and a response
that arrives anyway is ignored. The answer is the page (`text/html`, 2xx),
stamped by `native_forms`, and it morphs in by the rules above as a reply to
no component. A page for a query the address no longer shows is dropped
(`discarded`, reason `moved`), and so is one not later than the page shown
(`older-page`). The form is `aria-busy` while its read is on its way.

`"reveal": true` reads when an `IntersectionObserver` with a 200px margin sees
the form. After each read the form is watched again if the query it would
send differs from the address, and not while its own read is on its way.

`refresh_every(ms)` renders `<div hidden data-placebo-refresh-every="ms">`
(500 to 86400000). While the element is on the page, the runtime reads the page
again on that interval. A poll is skipped (`ignored`, reason `busy`) while a
read or refresh is in flight, and is paused while `document.visibilityState` is
`hidden` (`deferred`, reason `page-hidden`), reading once when the page is
shown. `placebo:scheduled` carries `source`: `user` or `reveal`; a refresh's
`placebo:applied` carries `source`: `push`, `interval`, or `moved`.

A link click within the site fetches the linked URL with
`X-Placebo-Refresh` (following redirects, `cache: "no-store"`), then pushes
the final URL with `history.pushState` and replaces `document.body` with the
answer's body; scripts in it run as on a load. The history entry carries a
key in `history.state.placebo`, under which the runtime keeps the scroll
position for Back and Forward, which fetch the entry's URL again the same way.
`history.scrollRestoration` is `manual` while the page is shown. A mutation
reply with `X-Placebo-Navigate` goes to its path the same way. The runtime
loads the URL natively instead when the answer is not `text/html`, the fetch
fails, or the answer's `<head>` scripts, styles, and stylesheets differ from
the page's as loaded. `placebo:navigated` carries `how` (`push`, `replace`,
or `restore`) and `reason`: `how` again when the page was shown, or why it
was loaded natively (`not-a-page`, `network-error`, or `head-changed`).

The Rust and browser halves must be upgraded together.

## Feeds

`Feed::mount` renders a hidden element with `data-placebo-feed`:

```json
{"version": 6, "feed": "tasks-live", "url": "/live/tasks?after=3f2a9c1b7d4e-41"}
```

A keyed feed of `Feeds` has the id `kind:key` and its own URL and position.

The runtime opens an `EventSource` for each mounted feed element and closes it
when the element goes. `Feed::changed` sends a `changed` event whose data is
`{"version": 6, "feed": id}`, with the event id `<instance>-<sequence>`. Called
from a mutation's handler, the data also has `"request"`: the runtime's
`X-Placebo-Request-Id` for that mutation. On a
connection, the feed compares `Last-Event-ID`, or else the mount's `after`
position, with its sequence: if the page missed a change, or the position is
from another server instance, it sends one `changed` event at once. A
subscriber that falls behind gets one `changed` event for everything it missed.

A page skips a signal whose `request` is a mutation it sent (`placebo:push`
with `push-own`): that mutation's reply is its page, which shows the change,
and reading the page again would only replace the reply's contents. If the
signal arrives while the mutation is on its way and its page then does not
show (its response was lost, or it shows in its component alone), the page is
read after all. On any other `changed`, the runtime GETs the current page URL with `Accept: text/html`
and `X-Placebo-Refresh: 6`; `native_forms` stamps the answer with
`X-Placebo-Rendered`. It morphs the page in by the rules for mutation replies,
as a reply to no form: every component takes it as a refresh from another
action. A page not later than the one shown is discarded (`discarded`, reason
`older-page`), and so is one for a query the address no longer shows
(`moved`). Signals during a refresh cause one more afterwards, and a refresh
waits for an IME composition to end. `placebo:push` events report
`push-connected`, `push-reconnected`, `push-changed`, and `push-own`; an applied refresh
emits `placebo:applied` with `source` set to `push` and the feed id as
`target`. A dropped connection logs the warning `push-disconnected` once; a
stream the browser gives up on logs `push-closed`.

## Idempotent retries

Every mutation form renders a hidden `placebo-key` with a fresh 128-bit key,
which a submission without JavaScript sends. The runtime sends a fresh key of
its own with each new submission instead, since markup a cache or another page
served can carry one key for several submissions. The adapter
claims the submission in the application's `ReplayStore` (by default an
in-memory store for ten minutes) before the handler runs, under an id made of
the key and a hash of the path and the body. The same key with another body is
a new submission. Cookies are not part of the id: they change between an
attempt and its retry (a refreshed session, an analytics cookie). A reply
(`reply`, `invalid`, or `conflict`) is recorded under the id with its status,
the reply (component, contents, and navigation) as JSON, and the headers the
handler added, such as `Set-Cookie`; any other response releases it. The handler runs to its end even if the browser
disconnects, so its reply is recorded for the retry. A repeated submission gets the recorded reply with
`X-Placebo-Replay: replayed` and its handler does not run; its page is rendered
again, and natively it becomes the same redirect or page. A repeat that arrives while the first is still
running waits up to five seconds for it. If the first has still not finished,
or stopped after claiming, the answer is 409 with `X-Placebo-Replay: pending`
(the runtime reports `replay-pending`), because running the handler again could
write twice. A store failure answers 503 with `X-Placebo-Replay: unavailable`
without running the handler.

A runtime retry sends `X-Placebo-Retry` with the milliseconds since its first
attempt. If the store has no record of the id and the first attempt is older
than the store's `window()` (for `MemoryReplays`, its time-to-live, or less
after replies were pushed out for capacity), the first attempt may have written
and been forgotten. The answer is 409 with `X-Placebo-Replay: unknown` (the
runtime reports `replay-unknown`) without running the handler. A store that
expires ids returns that expiry from `window()`; the default, `None`, trusts
that ids are kept.

The runtime remembers a stale component's uncertain request. Submitting the
same form again resends that request unchanged, body and key, and reuses its
snapshot of the controls, so edits typed in between are kept as edited since
submission. `placebo:scheduled` carries `retry: true` and `retryOf`, and
`placebo:applied` carries `replayed`.

The runtime emits `placebo:scheduled`, `request`, `applied`, `discarded`,
`deferred`, `ignored`, `push`, `warning`, and `error` events (each prefixed with `placebo:`).
Details contain action/target names and outcome, reason, or error code where
applicable. A mutation's `applied` also carries `refreshedLocal`,
`preservedLocal` (each with a `reason`), `refreshedComponents`,
`skippedComponents`, `page` (`whole`, `older`, `moved`, or `missing`),
`replayed`, and `navigate`; a read's and a refresh's carry the same summary
with `page: "whole"`. The example's interaction trace displays them.

Unexpected failures log actionable console errors by default. Enable execution
tracing from the browser console with `(await import('/placebo.js')).trace(true)`;
use `localStorage.setItem('placebo:trace', 'true')` before reloading to include
startup. Errors include request IDs and available method/path/status context,
plus whether a request started, an update applied, or a write's outcome is unknown.
Debug action routes log matching request IDs on the server. Unknown behaviors
are diagnosed; use `lazyBehavior()` for intentionally asynchronous registration.
See [diagnostics and the debugging evaluation](diagnostics.md).

HTML is trusted server output, not sanitizer input. Maud escapes text and
attribute values; applications own URL and executable-context safety. Inserted
script elements are inert; registered behaviors initialize declarative mounts.
The runtime is embedded in the Rust crate; in dev it
is served from its source file so JS edits reload without recompilation.
